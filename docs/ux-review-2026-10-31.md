# User experience and implementation review — 2026-10-31

## Scope and conclusion

Baseline: [`c4fa743f552c1d71db35fab791a2e63409bc1c3e`](https://github.com/chen-yu-hao/PyRPMD/commit/c4fa743f552c1d71db35fab791a2e63409bc1c3e)
on `main`. This review follows a user from installation through input creation,
validation, execution, saved-result analysis and restart. It also checks the
English/Chinese instructions against the actual public interfaces.

The repository already has valuable foundations: a shared TOML/Python job model,
explicit units, native/NumPy implementations, protected output directories,
scientific fingerprints, atomic checkpoint storage, and independent installed
wheel/source-distribution tests. The largest user-facing gaps were the lack of a
portable first calculation, checks occurring after work had started, and guidance
that had fallen behind the available commands and execution paths.

The review inventories all 110 package source/resource files, 19 native source/build/support
files, 183 test/support files, 100 examples and 17 workflows at the baseline. Static
review concentrates on the public CLI, input/unit/system resolution, workflow
dispatch, potential interfaces, FES analysis, checkpoint/restart boundaries and
packaging. The manuals, README files, examples and archived validation descriptions
provide the cross-checks. This is a repository-wide **usability and implementation
review**, not a new physical-convergence certification of every scientific method.

The separate, open [state-preparation hardening PR #44](https://github.com/chen-yu-hao/PyRPMD/pull/44)
already addresses preparation numerics, near-threshold QCT, failure accounting and
archive consistency. Its changes are not duplicated here. The experimental
[2D QTST PR #39](https://github.com/chen-yu-hao/PyRPMD/pull/39) is also outside this
PR's scientific scope.

## Resulting user workflow

After installation, the following commands work in any working directory:

```bash
python -m pyrpmd init my-first-run
python -m pyrpmd validate my-first-run/quickstart.inp --check-pes --output my-first-run/run
python -m pyrpmd run my-first-run/quickstart.inp --output my-first-run/run
python -m pyrpmd analyze my-first-run/run
python -m pyrpmd resume my-first-run/run
```

The starter uses a built-in harmonic potential, four beads, three umbrella
windows and two independent replicas per window. The expected saved summary has
`task="fes"`, `windows=3`, `streams=6`, `samples=120` and `converged=false`. These
counts verify the workflow; they do not establish physical convergence.

The generated input sets `output.directory="run"`, relative to that input. Thus
omitting `--output` produces the same destination. `init` accepts only a new or
empty directory, refuses a symbolic-link destination and never replaces existing
files. It prints shell-labelled next commands and their argument arrays. POSIX
commands use shell-safe quoting; Windows commands use PowerShell's call operator
and literal argument quoting. Actual Windows installation remains a follow-up
validation task.

`validate` and `prepare` retain their different output meanings:

- `validate --output DIR` previews a run directory; it does not initialize a run.
- `validate --write-resolved FILE` explicitly writes a resolved configuration.
- `prepare --output FILE` explicitly writes a preparation report.

Normal CLI results remain JSON on stdout. Expected input/runtime failures go to
stderr with status 2; a successful command returns 0. With `--debug`, the original
exception is re-raised for a traceback. Execution success and `valid=true` do not
assert `ready=true`, statistical convergence or physical applicability.

## Validation evidence

### Focused behavior regressions

The new suites are [`test_cli_ux.py`](../tests/test_cli_ux.py) and
[`test_runner_ux.py`](../tests/test_runner_ux.py). They exercise public entry points
and filesystem effects rather than only comparing helper output:

- A real subprocess starter run from a foreign working directory, including
  validation, sampling, analysis, identical completed resume and expected samples.
- Refusal to overwrite a populated destination, an existing file or a symlink.
- Shell argument handling, parser diagnostics, typo suggestions and `--debug`
  before/after nested commands.
- Validated absolute paths without creating the target output directory.
- Invalid umbrella/analysis/recording requests rejected before any provider call.
- Reanalysis failure preserving saved artifacts and checkpoints.
- Missing/partial run recovery guidance and checked parallel overrides.

The combined new suites plus the existing input/CLI and CV/FES suites passed
**42 test methods** locally, with no skips or errors.

Reproduction commands:

```bash
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 PYTHONPATH=src:tests \
  python -m unittest -v test_cli_ux test_runner_ux test_input_cli test_cv_fes

python -m pip install -e '.[test]'
python -m pytest -q
```

### Native and existing workflow regression

Both `_native` and `_thermal` compiled locally with C++17/OpenMP. `info` confirmed
all three integrators. A broad existing unittest run covered dynamics/native
parity, FES/CVs, dRPMD/rates/networks, PCET, initial states, state-selected workflows,
input/CLI, parallelism and units:

```bash
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 PYTHONPATH=src:tests python -m unittest -v \
  test_cli_native test_cv_fes test_drpmd test_dynamics test_equivalent_surfaces \
  test_initial_states test_input_cli test_mbar_rate_analysis test_parallel \
  test_pcet_science test_pcet_workflow test_periodic_materials test_potentials \
  test_prepare_buffer_ownership test_rate_workflows test_reaction_network \
  test_state_selected_check test_state_selected_input test_state_selected_native \
  test_system_units
```

This run executed 184 test methods: 179 passed, two i-PI tests were blocked at
`socket.socket(...)` by the execution environment, and three ASE methods skipped.
Two additional optional ASE/Torch classes skipped during `setUpClass`, giving the
raw footer `FAILED (errors=2, skipped=5)`. There were no assertion failures. This
qualified result must not be reported as a fully green suite.

### Installed package and documentation

A native Linux CPython 3.12 wheel was built and installed into a separate virtual
environment. Imports came from its `site-packages`, outside the checkout. The
console entry point completed the starter flow with 120 samples/6 streams/3
windows, preserved results on resume, and refused repeated initialization without
changing the input. All 112 final package source/resource files matched both the
wheel and the installed package byte-for-byte. The wheel
`pyrpmd-0.2.0-cp312-cp312-linux_x86_64.whl` has SHA-256
`4bf0c2a41b071a8a559e6041eb37006a7b8f0992c05e39a2345d00fdc5fa4d02`.

All 29 example `.inp` files resolve. The README/manual Python snippets parse, the
English/Chinese core chapter sets match, and the command tables cover all 15 CLI
commands. Strict English/Chinese HTML and single-page builds remain enforced by
the Documentation workflow. Installed wheel/source tests now exercise the same
starter independently of checkout-relative examples.

Local limitations: pytest, h5py and Sphinx were unavailable and normal dependency
installation could not retrieve them. Local tests used the real NumPy/SciPy stack
and compiled extensions; the starter exercised CSV/NPZ output. The PR's CI is the
gate for the full pytest, HDF5, MPI, optional-model and strict documentation checks.
Their status must be read from the actual run, not inferred from the local smoke.
